# loganalyzer.sh

Reads a plain-text log, writes a summary report. Bash, Linux.

## What it does

Given one log file, it reports:

- total lines
- lines containing `ERROR`
- lines containing `WARNING`
- top 5 IP addresses by count
- top 5 messages by count, with the timestamp stripped so identical messages
  group together

Output goes to the terminal and to `report.txt` at the same time. Each run is
appended, so the file builds up a history instead of being overwritten. Every
block starts with a `Run at:` timestamp and ends with a `---` rule, so you can
tell the runs apart.

## Run it

One argument, the log to analyze:

```sh
.local/bin/loganalyzer.sh sample.log
```

If it is not executable yet:

```sh
chmod +x .local/bin/loganalyzer.sh
```

Or skip the executable bit and call bash directly:

```sh
bash .local/bin/loganalyzer.sh sample.log
```

The report goes to `~/.local/state/loganalyzer/report.txt`. That path does not
depend on where you run the script from:

```sh
cd /tmp
$HOME/.local/bin/loganalyzer.sh $HOME/sample.log
# still writes to ~/.local/state/loganalyzer/report.txt
```

### Errors

Exits `1` with a message when:

- you pass anything other than exactly one argument
- the file does not exist
- the path is not a regular file, a directory for example
- the file exists but you cannot read it

Otherwise it exits `0`.

## Where the files go

```text
project/
├── README.md
├── sample.log                            <- test data for this exercise
└── .local/                               <- stands in for $HOME
    ├── bin/loganalyzer.sh                <- the script
    └── state/loganalyzer/
        ├── report.txt                    <- generated by the script
        └── cron.log               <- cron's record of its runs
```

The `.local/` directory here is a stand-in. It shows you the shape without
installing anything.

Careful: the script reads your *real* `$HOME`. Run it from this directory and
the report lands in your actual `~/.local/state/loganalyzer/`, not in the
`.local/` above. Examples written with `$HOME/...` assume you really installed
it there. The project-relative ones are safe to paste.

To **keep the output inside the project folder** override environment variable:

```sh
XDG_STATE_HOME="$PWD/.local/state" .local/bin/loganalyzer.sh sample.log
```

If you decide to copy file to user's home folder, for autocompletion on tab:

```shell
# Ubuntu 24
source ~/.profile
```

### Why these paths

This follows the [XDG Base Directory
Specification](https://specifications.freedesktop.org/basedir/latest/). It
sorts your files by what they are for instead of dumping everything in `$HOME`.

Both generated files sit in one `loganalyzer/` subdirectory so they cannot
collide with some other program's `report.txt`.

`sample.log` stays at the project root. It is test data for this exercise, and
a real home directory would never contain it.

The script picks its output directory like this:

```sh
state_dir="${XDG_STATE_HOME:-$HOME/.local/state}/loganalyzer"
```

`${VAR:-default}` means "use `VAR` if it is set, otherwise use this default".
You need the fallback.

## Cron line

Run the command by hand first, to be sure it works:

```sh
$HOME/.local/bin/loganalyzer.sh $HOME/sample.log >> $HOME/.local/state/loganalyzer/cron.log 2>&1
```

Add five time fields to the front and it becomes a cron line. They are
`minute hour day-of-month month day-of-week`:

```cron
USER_NAME=user_name
0 6 * * * /home/$USER_NAME/.local/bin/loganalyzer.sh /home/$USER_NAME/sample.log >> /home/$USER_NAME/.local/state/loganalyzer/cron.log 2>&1
```

**NOTE:** confirm project files have been moved to `$HOME/.local` before testing cron job

| Field | Value | Meaning           |
| ----- | ----- | ----------------- |
| min   | `0`   | at minute 0       |
| hour  | `6`   | of hour 6         |
| dom   | `*`   | every day         |
| mon   | `*`   | every month       |
| dow   | `*`   | every day of week |

So that runs at 06:00 every day. A few others:

```sh
*/15 * * * *   # every 15 minutes
0 * * * *      # top of every hour
0 6 * * 1      # 06:00 every Monday
```

### Installing it

`crontab -e` opens your personal crontab in an editor. Paste the line, save,
quit. Cron picks it up right away, no reload needed.

```sh
crontab -e     # add or edit jobs
crontab -l     # list what is installed
crontab -r     # remove your crontab entirely, careful
```

`crontab` is per-user. Jobs run as you, with your permissions.

On Debian and Ubuntu the file itself ends up at
`/var/spool/cron/crontabs/<username>`, owned by your user and mode `600`.

Use`crontab -e`, which checks your syntax before
installing and signals the daemon afterwards. A hand-edited file can be
silently ignored, and a broken line there stops the whole crontab.

### Why the line looks like that

Absolute paths, because cron starts the job in `$HOME` rather than where the
script lives. A relative path would land somewhere you did not expect. `$HOME`
itself is safe, one of the few variables cron sets.

`>> cron.log 2>&1` catches both output streams: `>>` appends standard
output, `2>&1` sends standard error to wherever standard output goes. Order
matters, the `2>&1` has to come after the `>>`. Drop it entirely and cron mails
you the output instead, which you will probably never read.

The script creates `~/.local/state/loganalyzer/` on its first run, so the cron
log has somewhere to land.

## Improvements I would make for a production system

1. Current script runs through `sample.log` file multiple times, this could be a bottleneck for large log files.
   - a single pass with awk and save data to file that can be parsed, sorted by multiple reports. (CSV or other delimiter, JSON Lines spec, etc)

2. `cron` job's `cron.log` - split out `stdout` and `stderr` into separate files with an identifier

3. Drop `.sh` extension from `loganalyzer.sh` in `bin` folder to match common convention

4. More reliable regex for IP addresses
